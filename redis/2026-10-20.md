# 좋아요 누르기

- GET 현재 좋아요 수
- 1 더하기
- SET 새 좋아요 수

incr: 안전하게 좋아요 수 증가시키기
레이스 컨디션(race condition)

# 싱글 스레드라면서?

- 레디스는 싱글 스레드이다 => 요리사 한 명이 주문을 하나씩 처리하는 것
- 레디스는 주문 한 장 한 장 완벽하게 처리했다.
- GET -> SET
  - 재고가 몇 개에요?
  - 그러면 재고 하나 빼서 2로 바꿔주세요.
- 레디스의 명령 하나는 절대 끊기지 않는다.
- 명령과 명령 사이에는 언제든 다른 요청이 끼어들 수 있다.

# 명령과 명령 사이의 틈을 없앴다면?

- 읽고 -> 빼고 -> 저장하는 걸 한 명령으로 퉁치면 되지 않을까?
- incr <-> decr
- 하나의 명령으로 더이상 쪼갤 수 없고, 중간에 기어들 수 없다. (atomic)
  - incr, decr, zincrby

# 모든 명령이 하나로 끝나지는 않는다.

- 게시글 본문, 좋아요 수 각각 다른 자료구조로 저장이 된 상태
- sorted set 좋아요 랭킹이 있다.
- 게시글이 지워지면?
  - 랭킹에서도 지워져야 함
  - 좋아요 수도 지워져야 함
    -> 명령어 하나로 처리할 방법이 없다.

# multi ~ exec

multi는 이미 무엇을 할 지 정해진 명령들을 끼어들기 없이 한 번에 실행할 때
쿠폰 문제처럼 중간에 값을 보고 판단해서 다음 명령을 고르는 것은 못함.
watch, lua script

- RDB(mysql)의 트랜젝션은 중간에 하나라도 실패하면 없던 일 (롤백 O)
- Redis의 트랜잭션은 중간에 하나가 실패해도 나머지는 성공함 (롤백 X)

# 트랜잭션 비교

Redis의 트랜잭션: 묶음 사이에 아무도 끼어들지 않는다.

- 중간에 끼어들기
  - MySQL, Rdeis: 막아줌
- 중간에 하나가 실패하면
  - MySQL: 롤백
  - Rdeis: 나머지는 그대로 실행됨

# 캐시 스탬피드

인기 상품의 캐시가 만료되는 순간, 인기 상품에 우르르 접속하는 경우 생기는 문제

- 모두가 캐시를 봤어 -> 없어
- 그래서 모두가 인기 상품을 조회하기 위해 SQL 실행 -> DB에 부하

# 캐시 스탬피드를 레디스로 막을 수 있을까?

- 우리가 막고 싶은 건 DB에 가서 조회하고 캐시를 채우는 것
  - 레디스 바깥에서 일어나는 일
  - 캐시가 채워지기까지 시간이 걸림

해결책: 다같이 캐시에 없는 걸 확인했어. 이 중에서 한 명만 다녀오자. 나머지는 기다리자.
-> **분산 락**

# 분산 락

- 자바에도 한 명만 들어와를 만드는 기능이 있다: synchronized
  - 한 프로세스 안의 스레드들끼리만 통함
- 우리가 쓰는 대부분의 서비스는 프로세스가 여러 개 (서버가 여러 대)
- 세션 저장소가 레디스를 쓰듯 공유할 수 있는 락 저장소도 레디스로
