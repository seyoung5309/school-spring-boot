# 지난 시가 정리

- 로그인 상태는 서버가 발급한 세션 ID를 통해 유지된다.
- 서버는 세션 ID <-> 사용자 정보 대응할 수 있는 세션 저장소를 갖고 있다.
- 서버가 여러 대일 때, 세션 저장소를 로컬 메모리로 하면 요청이 다른 서버로 갈 때마다 로그인이 풀린 것처럼 보인다.
- redis처럼 모든 서버가 함께 바라보는 하나의 저장소에 세션을 둬서 로그인 상태를 공유할 수 있다.

## 3. Redis의 저장 방법

### 3-1 RDB (기본값)

- 세이브 파일, 체크포인트
- 순간의 상태를 통째로 저장
- 마지막 세이브 이후에 진행한 건 날아감
- dump.rdb에 저장, 비교적 파일이 작고 불러오기가 빠름
- 대신 마지막 세이브가 언제 됐든 그 이후에 변경된 데이터는 사라짐

### 3-2 AOF (`redis-server --appendonly yes`)

- 처음부터 redis 명령어가 입력된 순서대로 적어놓음
- 서버가 다시 켜지면 똑같은 상태가 될 수 있도록 재생
- 리플레이 기록

- 3600 1: 3600초(1시간) 안에 1번 이상 바뀌면 세이브해라.
- 300 100: 300초(5분) 안에 100번 이상 바뀌면 세이브해라.
- 60 10000: 60초(1분) 안에 10000번 이상 바뀌면 세이브해라.
  -> 변경이 많을수록 자주 세이브합니다.
  -> 변경이 적으면 최대 한 시간 가까이 세이브를 안함.

**aof 안에 파일 읽기 (리플레이)**
`cat appendonlydir/appendonly.aof.1.incr.aof`

**변경 사항**
`redis-cli INFO persistence | grep rdb_changes_since_last_save`

## AOF는 그럼 절대 데이터를 잃어버리지 않을까?

- redis가 명령을 받으면 운영체제한테 넘김 (파일에 적어줘)
- 운영체제가 실제로 디스크에 새기는 주기가 있음 (기본 설정: 1초에 한 번)
- 정전처럼 컴퓨터(운영체제) 자체가 꺼지는 사고가 난다면 마지막 1초는 잃을 수도 있음
- 기본 설정을 바꿔서 더 안전하게 간다면? => 대신 그만큼 느려짐.

## RDB vs AOF

- incr: 값 1을 안전하게 올리는 것
  - rdb: value = 1000
  - aof: incr value \* 1000
  - AOF 파일이 너무 무거워짐
- redis는 가끔 기록을 정리한다. (bgrewriteaof)
  - aof 모드라도 세이브 파일 형태로 지금 상태를 새로 만듦(RDB)
  - 그 뒤로 들어오는 명령은 기록
  - 요즘 redis의 AOF는 RDB + 리플레이 기록
- 저장하는 것
  - RDB: 특정 순간의 상태 전체 (스냅샷)
  - AOF: 들어온 명령 하나하나
- 강제 종료 시
  - RDB: 마지막 세이브 이후 데이터 손실
  - AOF: 거의 손실 없음
- 파일 크기
  - RDB: 작음
  - AOF: 큼
- 서버가 다시 켜질 때
  - RDB: 빠름
  - AOF: 느림 (명령을 다시 실행해야 하니까)
