- 순서가 없고, 중복도 없는 값 여러 개

- 필드-값 여러 쌍

## Sorted Set

   - 순서 -> List
   - 중복 -> Sorted Set

## 비유하기

- 편의점 계산대 옆에 진열대 (껌, 사탕, 담배, ...)

## 기술로 옮기기

- Redis: 메모리 / MySQL: 디스크
- 속도: 메모리 >>>>>>>>>> 디스크
- 원본은 디스크에 두되(상품 재고는 창고), 자주 조회되는 데이터만 메모리에 저장(계산대 옆)

## 다른 장점

- 인기 상품 페이지: 1초에 만 명이 동시 접속
- 캐시가 없다면
  - 접속할 때마다 쿼리
  - 1초에 만 번 쿼리
- 캐시가 있다면
  - 처음 한 명은 DB에 가서 조회
  - 나머지 9999명은 Redis에 있는 복사본 조회
- DB는 한 번만 일함

## 캐시의 목적

1. 응답 속도가 빨라진다.
2. 원본 저장소의 부하가 줄어든다.

# 캐시의 기본 구조

시나리오: 상품 101번의 정보를 조회할 경우이다.

## 1. DB로 조회할 때

1. 요청이 들어온다. (상품 101번 정보)
2. DB에 SELECT 쿼리를 요청한다.
3. 결과를 반환한다.

## 2. 캐시를 쓸 때 (cache-aside)

1. 요청이 들어온다. (상품 101번 정보)
2. Redis(캐시)에 있는지 확인한다.
   1. 있으면 반환 (캐시 히트)
3. DB에 SELECT 쿼리를 요청한다. (캐시 미
4. 조회한 결과를 Redis에 저장한다.
5. 결과를 반환한다.

# 시나리오

- 키보드 상품 페이지
- 아직 아무것도 안 본 인간이 있다.
- 아직 아무도 상품 페이지를 본 적 없다.
- 1번 손님이 101번 키보드 상품을 조회한다.

## 캐시에도 유통기한이 필요하다

### 정보 변경

- 무선 키보드가 45만원 일떄에 해시에 저장됐는데, 5분 뒤에 30만원으로 세일한다면
- 손님한테는 게속 45마원으로 보여줌
- 캐시게 언제나 그렇게 저장돼었으니가
  -> 캐시를 쓰는 이상 향상 위험
- 그럼 모드 데이터를 TTL에 30초를 주면 어덯게 될까?
- 아니다.
- 자주 바뀌는 데이터라면 TTL을 더 짧게 가져가서 정보의 간극이 없게 하고
- 거의 안 바뀌는 데이터라면 TTL을 더 길게 가져가서 캐시 미스가 없도록 해야 함.

### TTL이 너무 짧으면

- 캐시가 자주 비어 있음
- 그만큼 캐시 미스가 자주 일어남
- 캐시를 쓰는 의미가 없음
  TTL은 캐시가 얼마나 신선한지(신선도)와 데이터 베이스의 부하 사이의 줄 다리기 -

  - 유통기한이 너무 짧으면 데이터베이스를 너무 자주 조회해서 캐시 의미가 없다.
