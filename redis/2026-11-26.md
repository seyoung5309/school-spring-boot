# Redis

## 1. Redis란?, 왜 빠른가?

- Redis는 보통 RDB와 함께 사용한다. (원본: RDB에 저장)
- key-value 방식의 인메모리, 싱글 스레드
- 인메모리의 함정: 재시작하면 데이터가 사라진다.
- 싱글 스레드의 함정: 하나의 부하 -> 전체의 부하

### Q. Redis는 왜 쓸까요?

Redis는 key-value 방식의 인메모리 데이터 방식과
싱글 스레드 동작으로 빠른 처리가 가능합니다.
TTL과 다양한 자료구조를 제공한다.

### MySQL 없이 Redis만 사용하면 안될까요?

메모리 기반이라 강제 종료 시 데이터가 날아간다.
MySQL은 있는 롤백 트랜잭션이 없다.
돈, 주문과 같이 정확성이 중요한 데이터 원본은 MySQL에 저장하는 게 안전하다.

# 2. 자료구조

메인 자료구조 종류: string, hash, set, sorted set, list
자료구조를 고르는 기준 (= 무엇을 막고 싶은가)

- 데이터가 여러 개인가?
- 중복되도 괜찮은가?
- 하나에 여러 뭉치가 들어있는 데이터인가?
- 순서가 중요한가?

### Q. 실시간 랭킹은 어떤 자료 구조로 만들까요?

sorted set으로 만들면 좋을 것이라고 생각한다.
자료 구조 자체가 순서를 지키는 방식이고,
여기에 날짜를 함께 넣어서 2026112601과 같은 식으로 하면 좋다.

- sorted set
- 점수를 올리는 명령어: zincrby
- 점수를 기준으로 정렬이 된다. (order by 필요 없음)
- 정렬된 순서로 조회하는 명령어(내림차순) : zreverange

### Q. 좋아요 수를 Get 해서 +1 Set 하면 안되는 이유

# 3. 캐시

- 목적: 빠르게 조회하기 위해, DB 부하를 줄이기
- cache-aside: 캐시 조회 -> 없으면(캐시 미스) DB 조회 후 캐시 저장 -> 있으면 캐시만 조회(캐시 히트)
- TTL 필수
- 문제점
  - 캐시 스탬피드 (키 하나)
  - 캐시 침투 (없는 키)
  - 캐시 쇄도 (여러 키)

### Q. 캐시가 DB 부담을 줄였다는 것을 어떻게 증명할 수 있을까.

복잡하고 데이터를 많이 조회하는 쿼리문을 한 명만 조회해오고 캐시에 저장함으로서
다른 사람들은 그 쿼리문으로 직접 DB에 접근하는 것이 아니라 캐시에 있는 내용을 불러올 수 있게 된다.
이를 통해서 효율성이 좋다.

- DB 호출 횟수를 세면 된다.

# 4. 세션, 영속성, 동시성

- 세션: 세션 아이디(쿠키) + 보관함(redis). 서버가 여러 대여도 같은 Redis를 보게 한다. (세션 공유)
- 영속성:
  - **RDB**: 세이브 파일
  - AOF: 리플레이 기록
- 동시성: 명령 하나는 안 끊김, 명령 사이에는 끼어든다.

### Q. 서버가 두 대 이상일 때, 로그인을 유지하는 방법

세션을 서버 메모리에 두면 다른 서바로 요청이 갈 때 로그인이 사라진다.
모든 서버가 함꼐 보는 저장소 -> redis
쿠키에 담긴 세션 아이디가 어느 서버든 같은 세션을 찾음
8080 로그인 -> 8181 로그인

# 5. 메모리, 고가용성, 확장

redis: 메모리가 꽉차면 - noeviction - allkeys-lru - volatile-lru

보편적인 방법: 캐시 TTL + volatile-lru

고정 댑: 레플리카 + 센티넬 (자동 페일오버)

메모리 부족: 클러스터

### 마스터가 죽으면 서비스는 어떻세 될까요?>

서버의 마스터가 레플리카 중 하나로 이전된다. 또한 마스터였던 서버는 재시동 후에는 레플리카로 접속되며,
마스터가 한 대 뿐이면 다시 켤 때까지 서비스가 멈춘다.
마스터-레플리카 보게본을 두고, 센티넬이 감시한다.
센티넬이 레플리카를 자동으로 마스터로 승격
