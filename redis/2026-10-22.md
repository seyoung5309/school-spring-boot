# 지난 시간 정리

1.  Redis의 명령 하나는 안 끊기지만, 명령 사이에는 끼어든다.
2.  명령 하나로 가능한 경우(원자적, atomic): incr, decr, zincrby
3.  명령 여러 개를 끼어들기 없이 묶으려면: multi ~ exec (Redis 트랜잭션)
4.  Redis 밖의 일을 한 명만 하게 하려면: set {KEY} nx ex {SECONDS} (분산락)

- ttl을 안 붙이면 키가 영원히 남는다.
- ttl 없는 키가 Redis의 계속 쌓인다면 -> 공간 낭비

# 이번 시간

Redis는 인메모리 데이터베이스
메모리가 꽉차면 무슨 일이 일어날까?

```
redis-server --save ""
```

**메모리 확인 명령어**

```
redis-cli info memory | grep -E "used_memory_human|maxmemory_human|maxmemory_policy"
```

**결과**

```
memory_human|maxmemory_policy"
used_memory_human:917.18K
maxmemory_human:0B
maxmemory_policy:noeviction
```

=> (여기서 maxmemory_human:0B의 0B은 제한이 없다.)

# maxmemory_polisy

## noeviction

- 기본값
- 메모리가 꽉차도 아무것도 버리지 않는다.
- 꽉 찬 상태에서 새로 저장하는 명령은 거절

## allkeys-lru

- LRU: least recently used (가장 오래 안 쓴 것)
- LFU: least frequently used (가장 덜 자주 쓰는 것)
- 메모리가 꽉 차면 모든 키 중에서 가장 오래 안 쓴것부터 버림

## volatile-lru

- volatile: 언젠가 사라질 예정인 것(ttl이 있는 것)
- 메모리가 꽉차면 ttl이 있는 키 중에서 가장 오래 안 쓴 것부터 버림

## volatile-ttl

- 메모리가 꽉 차면 ttl이 있는 키 중에서 ttl이 가장 임박한 것부터 버림

- 세션과 캐시를 같은 레디스에서 쓴다면 allkeys-lru는 적합하지 않을 수 있므.
- 캐시처럼 없어져도 원본 데이터에서 가져올 수 있는 것만 ttl을 부이고 volatile 정책
