## 세션 로그인

- 아이디 + 비밀번호 1회 로그인
- 서버가 세션ID를 만들어 줌.
- 쿠키 안에 세션 ID
- 이후 모든 HTTP 요청 브라우저가 세션 ID를 함께 보내 (자동)
- 서버는 세션 ID만 보고 이 사람이 A 유저라고 알아볼 수 있다.
  - 세선 ID <-> 유저 정보 저정해놔야 알 수 있음.
  - 서버 메모리

- 세션 ID를 왜 무작위로 만들까?
  - 우리가 아는 유저 아이디, 학번 같은 걸로 사용해도 되지 않나?
  - 유저 아이디, 학번 같은 인지 가능한 문자열은 복제해서 사칭할 수 있음
  - 서버가 무작위로 만들면 추측하기 어려움

## Redis 자료구조 -> hash

redis는 세션 관리 목적으로 이용이 가능하다.
세션이 필요한 이유는?

- 서버 한 대로 이뤄지는 서비스가 아니다.
- 서버가 여러 대 있을 때, 서버끼리 이 사람이 로그인을 했는지 안했는지 공유하기 위해서

## 서버가 왜 여러 대여야 하는가?

- 서버가 죽어도 다른 서버에서 돌아가야 하니까
- 이용자가 늘어나면 서버 한 대로 감당이 안되니까

서버가 여러 대 일때, 어떻게 요청을 분산해서 처리하는가?

- 로드밸런서
- 로드밸런서가 요청을 먼저 받아서 서버들한테 나눠줌.
- 그 말인 즉슨, 내 요청이 항상 같은 서버로 간다는 보장이 없음.

서버 1, 2, 3번이 각각 누가 로그인했는지를 공유하지 않는다면,
서버 1번에서 로그인한 사람이 누구인지 모른다.

각 서버가 세션을 자기 로컬 메모리에만 저장하면, 서버 간 로그인 상태가 공유되지 않는다.

- 로드밸런서가 사용자를 구분하면 안되나?
- 로드밸런서가 같은 사용자의 요청을 항상 같은 서버로만 보내면 안되나?
  - 스티키 세션: 로드밸런서가 같은 사용자의 요청을 항상 같은 서버로 보내는 방법
    - 서버가 고장나면?
      - 돌아올 때까지 못 씀
      - 고장날 때 다른 서버로 옮기는 옵션을 넣는다고 해도 전부 로그아웃 됨.
    - 부하가 고르게 나눠지지 않음
      - 1번 서버에는 유난히 서비스를 오래 쓰는 사람들만 있다면?
      - 2번 서버에는 한 번만 들어왔다가 나가는 사람들만 있다면?
      - 1번 서버로 부하가 몰린다.

문제의 원인: 서버가 각자 자기만 아는 저장소(메모리)를 쓴다는 걸
해결 방법: 모든 서버가 같은 곳을 보고 공유

| 무작위 문자열 생성: `SESSION_ID=$(uuidgen)`
| 예시 값: `6b893a59-6af0-4e7d-b144-c77b4242ec39`

## 왜 하필 Redis인가?

지금까지 한 것

- 서버가 커지면 -> 서버를 당연히 여러 대 띄워야 함.
- 서버가 2개 이상이 되면 -> 서로의 메모리에 접근할 수 없음.
- 로그인과 같이 서버끼리 공유해야 하는 정보가 있음.
- 그래서 Redis라는 공유 메모리를 써서 저장을 했음.
