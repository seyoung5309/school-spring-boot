# 프록시
- 진짜 객체 대신 호출을 받아서,
- 앞뒤로 무언가를 하고,
- 진짜 객체에게 일을 넘김 

[우리가 생각한 것]
PostController -> getPosts() -> PostService

[실제]
PostController -> getPosts() -> PostService$$SpringCGLIB -> PostService
- 앞: 시간 재기 시작, 트랜잭션 시작
- 뒤: 실행 시간 출력, 커밋/롤백 

# 프록시는 언제 생길까? 
- PostService 객체를 만들고 나서(bean)
- 이 bean에 걸리는 aspect가 있나?
  - 없으면 -> 진짜를 그대로 빈으로 등록 (BCryptPasswordEncoder)
  - 있으면 -> 대역을 만들어서 대역을 빈으로 등록 (PostService)
- PostController 빈을 만들 때 PostService 프록시가 들어간 것

# 왜 안에서 본 PostService는 진짜일까? 
PostController -> proxyTest() -> [proxy] aspect 실행 -> 진짜 Service.proxyTest() -> this.getALlPosts() 
- getAllPosts()는 자기 호출. 직접 실행했기 때문에 proxy를 안 거침
- 실행 시간이 안 찍힘 

# @Transactional 
- "여기 트랜잭션 필요해요" 표시 
- 트랜잭션을 시작하고 커밋/롤백은 스프링이 만들어둔 aspect가 함 
- 그 aspect를 실행하는 건 스프링이 세운 대역, proxy가 함
- 프록시를 안 거치면 트랜잭션도 없음
- "스프링이 다 해준다"가 아님 

- 컨트롤러랑 진짜 서비스 사이에서 누가 aspect를 실행했을까? 
  - 프록시 
  - 스프링이 만든 대역
  - 진짜를 상속한 자식 클래스가 메서드를 오버라이딩
  - aspect 앞 -> 진짜 -> aspect 뒤
- aspect가 실행되지 않는 경우도 있을까? 
  - 있다. 
  - 같은 클래스 안에서 부르면(자기 호출) 프록시를 거치지 않아서 aspect, 트랜잭션이 빠진다.

# 스프링 vs 스프링 부트
- 하는 일
  - 스프링: 컨테이너, DI, DispatcherServlet, 트랜잭션, AOP, 프록시
  - 스프링 부트: 자동 설정, 스타터(의존성 묶음), 내장 톰캣 application
- 비유
  - 스프링: 엔진과 부품 
    - 프록시를 만드는 기능 
  - 스프링 부트: 부품 조립해서 바로 쓸 수 있께 출고 
    - 의존성이 있을 때 기능을 켜주는 것
  - 스프링 부트가 없어도 스프링은 잘 돌아감
    - 오늘 본 200+개 빈을 우리가 지겁 설정해야 함

-우리가 안 만들었던 객체들(빈) 누가 만들었을까?  
  - 스프링 부트의 자동 설정
  - @EnableAutoConfiguration이 조건에 맞는 설정을 켜거 빈을 만듦. 
  - 의존성 한 줄이 왜 동자글 바꿀까?
    - 의존성(build.gradle)과 설정(application.yml)이 자동 설정의 조건이기 때문
