# 완성 기준

1. 성공(조회, 수정, 저장, 삭제): 200 / 201 / 204
2. 클라이언트 잘못 요청: 400
3. 로그인 안함 (누군지 모름): 401
4. 남의 것(누군진 아는데 안됨): 403 
5. 그런 것 없다: 404
6. 서버가 잘못함: 500 (서버 버그)

# 2, 6, 8번 고칠 때 특징

- 예외가 발생했을 때 응답을 바꾸는 건 GlobalExceptionHandler
- 이 사람 것인가? 검사하는 건 Service
- DB에서 어떻게 가져올지 Repository

# API 요청 하나가 DB까지 다녀오는 길

- 수업을 절반 했을 때 
postman -> dispatcherServlet -> Controller -> Service -> Repository -> H2

- 지금 (가는 길)
postman -> 톰캣 -> Filter(Spring Security) -> dispatcherServlet -> loginInterceptor -> 
-> 값을 꺼내 넣기(어노테이션) -> PostController -> [proxy] 실행 시간, 트랜잭션 -> PostService -> 
-> [proxy] PostRepository -> Hibernate -> HikariDataSource/JDBC -> H2

- 지금 (오는 길) 
H2 -> DB에서 온 행 -> Entity -> [Service] DTO -> [proxy] 프록시가 커밋하고 실행 시간 찍기 -> 
-> JSON으로 바꾸기 -> 201/200/204 

- Controller에 데이터를 전달하는 어노테이션: RequestBody @Valid @SessionAttribute @Pageable, ... 

# 에러 났을 때
- 실행 시간 로그 찍혔다면: Service 까지는 갔다.
- SQL이 찍혔다면: DB 까지는 갔다. 

- 상태 코드: 뭐가 잘못됐나
- 로그: 어디서 멈췄나 
- 막을 수 있으면 최대한 앞에서 막는다. (로그인 안 한 사람을 DB까지 보낼 필요는 없다.)

1. 로그인 안하고 게시글 저장: loginInterceptor
2. 로그인 하고 게시글 저장 title "": dispatcherServlet(@Valid)

# IoC, DI: 
  - 클래스는 만들고 new 한 적 없음. 전부 스프링이 빈으로 만들어 준 것. 생성자로 주입받은 것
  - 만들고 연결하는 주도권 스프링 컨테이너에 있다. 

- 트랜잭션, AOP, 프록시
  - @Transactional: "여기 트랜잭션 필요해요" 표시 (Service)
  - aspect: 앞뒤에 끼어드는 일(실행 시간 로그)
  - 프록시: aspect를 실행하기 위해 스프링이 세운 대역
